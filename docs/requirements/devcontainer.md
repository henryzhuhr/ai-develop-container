# Dev Container 需求

总入口见 [requirements.md](../requirements.md)。

## 1. 背景

当前目标是让用户使用本地 VS Code 通过 Dev Containers / Remote Development 进入该容器时，尽量减少首次连接时的准备时间，并尽可能避免或缩短 `VS Code Server` 的在线下载过程。

需要明确的一点：

- 本场景使用的是微软的 `VS Code Server`
- `VS Code Server` 通常与用户本地 VS Code 客户端版本或 commit 绑定。
- 因此，“完全不下载”只有在客户端版本被严格控制时才有较高可行性；如果客户端版本不固定，仍可能发生重新下载。

本需求文档用于补齐 Dev Container 场景下的目标、约束、实现边界和待确认信息，作为 `R-011` 的实现依据。

## 2. 目标

- 让容器成为可直接用于远程开发的目标环境。
- 让用户连接容器后无需再安装 Go、Java、Python、AI CLI 等核心依赖。
- 优先降低首次进入容器的准备成本。
- 为后续 `.devcontainer/` 模板和远程开发体验优化预留结构。

## 3. 非目标

- `DC-NG-001` 第一阶段不保证完全不下载 `VS Code Server`。
- `DC-NG-002` 第一阶段不处理浏览器版 IDE。
- `DC-NG-003` 第一阶段不处理完整扩展离线分发。

## 4. 需求项

### 4.1 容器开发体验

- `DC-001` 容器必须具备远程开发所需的核心工具链。
- `DC-002` 应明确推荐的工作目录和挂载方式。
- `DC-003` 应保证 `docker run` 和 `docker compose` 场景都能作为远程开发基础环境。

### 4.2 Dev Container 配置

- `DC-004` 第二阶段建议补充 `.devcontainer/` 模板。
- `DC-005` 模板中应定义基础工作目录、推荐用户和必要扩展。

### 4.3 用户模型

- `DC-006` 第一阶段默认覆盖 `root` 用户场景。
- `DC-007` 后续评估是否补充非 `root` 用户方案。

## 5. 已知技术约束

这些约束会直接影响实现方案。

### 5.1 VS Code Server 与客户端版本绑定

- `DC-C-001` Remote Development 连接远端时，会使用与本地 VS Code 匹配的 server 版本。
- `DC-C-002` 如果用户本地 VS Code 版本升级，对应 server 版本也可能变化。
- `DC-C-003` 如果镜像中未预置对应版本，首次连接仍会触发下载。

### 5.2 “预置 server”有前提

- `DC-C-004` 路径 A：锁定组织内统一的 VS Code 版本，然后在镜像中预置对应 commit 的 `~/.vscode-server/bin/<commit>`。
- `DC-C-005` 路径 B：接受首次连接时仍可能下载，但把其他依赖和常用扩展都预装，尽量缩短初始化时间。

### 5.3 许可、分发与来源限制

- `DC-C-006` 若要在镜像构建时预置 `VS Code Server`，需要明确下载来源、版本管理方式和许可风险。
- `DC-C-007` 如果使用环境需要内网、离线或镜像代理，需要一并定义制品来源与缓存策略。

## 6. 已确认信息

以下信息已经由你补充，可直接作为实现输入：

### 6.1 用户环境

- `DC-I-001` 用户操作系统：支持 macOS 和 Linux，不支持 Windows。
- `DC-I-002` 本地 VS Code 渠道：默认 `Stable`。
- `DC-I-003` 版本策略：需要支持多个 VS Code 版本，但第一阶段建议先锁定一个版本实现。
- `DC-I-004` 升级策略：不允许自动升级；第一阶段仅包含预置版本，后续通过构建参数或版本映射支持更多版本。
- `DC-I-005` 网络环境：镜像构建环境是公网；用户运行环境是内网或离线，因此需要支持离线使用场景。

### 6.2 安全与合规

- `DC-I-006` 允许在镜像构建时访问外网。
- `DC-I-007` 不要求必须走内部制品源或镜像源。
- `DC-I-008` 当前无额外许可证或供应链审计要求。

## 7. 候选实现方案

### 7.1 推荐默认决策

在你没有提供更多约束前，我建议先按下面的决策推进第一版：

- `DC-D-001` 默认选择“锁定一个 VS Code 版本并预置对应 server”的方案。
- `DC-D-002` 本地 VS Code 默认限定为 `Stable` 渠道。
- `DC-D-003` 第一阶段默认锁定 1 个明确的 VS Code 版本与 commit。
- `DC-D-004` 默认优先支持 `amd64`，如有明确需要再补 `arm64` 或多架构。
- `DC-D-005` 默认覆盖容器内 `root` 用户。
- `DC-D-006` 默认允许镜像构建阶段访问外网下载 `VS Code Server` 制品。
- `DC-D-007` 默认不处理浏览器版 IDE。
- `DC-D-008` 默认不处理第三方扩展的完整离线分发，只保留后续扩展点。
- `DC-D-009` 当本地 VS Code 版本与镜像预置版本一致时，不再下载 server。
- `DC-D-010` 当本地 VS Code 版本变化时，允许 Remote Development 按需重新下载对应 server。

### 7.2 方案 A：锁定本地 VS Code 版本并预置对应 server

- `DC-S-A-001` 在镜像构建时下载指定 commit 的 `VS Code Server`。
- `DC-S-A-002` 放入约定目录，例如 root 用户下的 `~/.vscode-server/bin/<commit>`。
- `DC-S-A-003` 适合内部统一开发环境和离线场景。

### 7.3 方案 B：不预置 server，只优化首次初始化体验

- `DC-S-B-001` 不尝试预埋 `VS Code Server`。
- `DC-S-B-002` 优化镜像内容，例如常用工具链、shell、git、语言依赖、扩展缓存、工作目录结构。
- `DC-S-B-003` 维护成本更低，但首次连接仍可能下载 server。

### 7.4 方案 C：同时支持在线与离线模式

- `DC-S-C-001` 在线环境默认按需下载。
- `DC-S-C-002` 离线环境通过构建参数、挂载缓存或制品仓库注入指定 server。
- `DC-S-C-003` 灵活，但实现复杂度和文档成本更高。

## 8. 验收标准

- `DC-A-001` 用户可使用本地 VS Code 连接正在运行的容器。
- `DC-A-002` 用户连接容器后无需再安装 Go、Java、Python、AI CLI。
- `DC-A-003` 文档中明确当前远程开发使用方式和限制。
- `DC-A-004` 如果实现了预置 `VS Code Server`，则需要验证匹配版本下首次连接不再下载 server。

## 10. 待决策项

### 10.1 版本与制品信息

- `DC-Q-001` 第一阶段锁定的目标 VS Code 版本是多少。
- `DC-Q-002` 对应的目标 commit 是多少。
- `DC-Q-003` 如果一个版本不够，第二阶段是否需要同时支持多个版本预置。

参考建议：

- 第一阶段先锁定一个 `Stable` 版本，避免把“多版本预置”和“离线支持”同时做复杂。
- 如果你暂时只知道版本号，不知道 commit，也可以先提供版本号，后续由实现阶段补齐映射。

我的决策：

- `DC-Q-001` and `DC-Q-002` 目前只需要支持如下即可：

```bash
版本: 1.112.0
提交: 07ff9d6178ede9a1bd12ad3399074d726ebe6e43
日期: 2026-03-17T18:09:23Z
```

### 10.2 容器运行约定

- `DC-Q-004` 第一阶段目标架构是否先固定为 `amd64`。
- `DC-Q-005` 第一阶段运行方式是否只支持 `Docker + VS Code Dev Containers`。
- `DC-Q-006` 默认工作目录最终定为哪个路径。
- `DC-Q-007` 是否要求开箱即用提供 `git / ssh / zsh / sudo` 中的哪些工具。

参考建议：

- 第一阶段先固定 `amd64`。
- 第一阶段只承诺 `Docker + VS Code Dev Containers`。
- 工作目录建议统一为 `/workspace`，不要继续沿用仓库名耦合路径。
- `git` 和 `ssh` 作为必需项；`zsh`、`sudo` 作为可选项。

我的决策：

- `DC-Q-004` 考虑 `amd64` 和 `arm64` ，但是实际上 `scripts/docker-build.sh` 已经区分了，因为我开发这个项目是在 M1 Mac 上的。但是使用的是在 Linux amd64 上构建的 `amd64` 镜像
- `DC-Q-005` 第一阶段只承诺 `Docker + VS Code Dev Containers`。
- `DC-Q-006` 工作目录继续沿用仓库名耦合路径，用户自己配置就行，不需要我们项目考虑，例如用户自己的项目里 `docker-compose.yml` 里自定义挂载
- `DC-Q-007` 这些工具已经在 `dockerfiles/Dockerfile` 构建，先保持不变

### 10.3 远程开发体验边界

- `DC-Q-008` 第一阶段是否要交付 `.devcontainer/` 模板。
- `DC-Q-009` 第一阶段是否接受继续使用 `root` 用户。
- `DC-Q-010` 是否需要预置任何 VS Code 扩展或扩展缓存。
- `DC-Q-011` 是否允许把 `VS Code Server` 制品内置到公开镜像。

参考建议：

- `.devcontainer/` 模板建议第一阶段就做。
- 第一阶段建议接受 `root` 用户，先把可用性做通。
- 扩展和扩展缓存第一阶段建议不做。
- 如果镜像会公开分发，建议先明确 `VS Code Server` 制品内置策略再实现。

我的决策：

- `DC-Q-008` 第一阶段要交付 `.devcontainer/` 模板。
- `DC-Q-009` 第一阶段接受继续使用 `root` 用户。
- `DC-Q-010` 第一阶段不预置任何 VS Code 扩展或扩展缓存。
- `DC-Q-011` 第一阶段不允许把 `VS Code Server` 制品内置到公开镜像。
