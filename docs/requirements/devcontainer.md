# Dev Container 需求

总入口见 [requirements.md](../requirements.md)。

## 1. 背景

当前目标是让用户使用本地 VS Code 通过 Dev Containers / Remote Development 进入该容器时，尽量减少首次连接时的准备时间，并尽可能避免或缩短 VS Code Server 的在线下载过程。

需要明确的一点：

- 本场景使用的是微软的 `VS Code Server`，不是 Coder 的 `code-server`。
- `VS Code Server` 通常与用户本地 VS Code 客户端版本或 commit 绑定。
- 因此，“完全不下载”只有在客户端版本被严格控制时才有较高可行性；如果客户端版本不固定，仍可能发生重新下载。

本需求文档用于补齐约束、目标和验收标准，作为后续实现依据。

## 2. 目标

- 让容器成为可直接用于远程开发的目标环境。
- 让用户连接容器后无需再安装 Go、Java、Python、AI CLI 等核心依赖。
- 为后续 `.devcontainer/` 模板和远程开发体验优化预留结构。
- 你希望“无需再次下载”达到什么程度：
  - 例如：完全离线可进入。
  - 或：大多数情况下不下载，只有 VS Code 版本变化时才下载。

## 3. 非目标

- 第一阶段不保证完全不下载 `VS Code Server`。
- 第一阶段不处理浏览器版 IDE。
- 第一阶段不处理完整扩展离线分发。

## 4. 需求项

### 4.1 容器开发体验

- `DC-001` 容器必须具备远程开发所需的核心工具链。
- `DC-002` 应明确推荐的工作目录和挂载方式。
- `DC-003` 应保证 `docker run` 和 `docker compose` 场景都能作为远程开发基础环境。

### 4.2 Dev Container 配置

- `DC-004` 第二阶段建议补充 `.devcontainer/` 模板。
- `DC-005` 模板中应定义基础工作目录、推荐用户和必要扩展。

### 4.3 用户模型

- `DC-006` 第一阶段默认覆盖 `root` 用户场景。
- `DC-007` 后续评估是否补充非 `root` 用户方案。

## 4. 已知技术约束

这些约束会直接影响实现方案，请确认是否接受：

### 4.1 VS Code Server 与客户端版本绑定

- Remote Development 连接远端时，会使用与本地 VS Code 匹配的 server 版本。
- 如果用户本地 VS Code 版本升级，对应 server 版本也可能变化。
- 如果镜像中未预置对应版本，首次连接仍会触发下载。

### 4.2 “预置 server”有前提

常见可行路径通常有两类：

- 路径 A：锁定组织内统一的 VS Code 版本，然后在镜像中预置对应 commit 的 `~/.vscode-server/bin/<commit>`。
- 路径 B：接受首次连接时仍可能下载，但把其他依赖和常用扩展都预装，尽量缩短初始化时间。

### 4.3 许可、分发与来源限制

- 若要在镜像构建时预置 VS Code Server，需要明确下载来源、版本管理方式和许可风险。
- 如果你的使用环境需要内网、离线或镜像代理，需要一并定义制品来源与缓存策略。

## 5. 候选实现方案

请在下面选择或补充你更倾向的方案。

### 推荐默认决策

在你没有提供更多约束前，我建议先按下面的决策推进第一版：

- 默认选择方案 A。
- 本地 VS Code 默认限定为 `Stable` 渠道。
- 默认锁定 1 个明确的 VS Code 版本与 commit。
- 默认优先支持 `amd64`，如有明确需要再补 `arm64` 或多架构。
- 默认覆盖容器内 `root` 用户。
- 默认允许镜像构建阶段访问外网下载 VS Code Server 制品。
- 默认不处理浏览器版 IDE。
- 默认不处理第三方扩展的完整离线分发，只保留后续扩展点。
- 默认接受以下行为：
  - 当本地 VS Code 版本与镜像预置版本一致时，不再下载 server。
  - 当本地 VS Code 版本变化时，允许 Remote Development 按需重新下载对应 server。

如果你同意这组默认值，我会按这条路径直接实现第一版。

### 方案 A：锁定本地 VS Code 版本并预置对应 server

说明：

- 在镜像构建时下载指定 commit 的 `VS Code Server`。
- 放入约定目录，例如 root 用户下的 `~/.vscode-server/bin/<commit>`。
- 适合内部统一开发环境。

优点：

- 首次连接最快。
- 更容易支持离线或弱网环境。

代价：

- 需要维护 VS Code 版本与 commit 的映射。
- 用户本地 VS Code 版本不一致时，仍可能重新下载。

请补充：

```text
是否选择：建议默认选“是”
目标 VS Code 版本：待你指定；若暂未指定，实现时可先预留构建参数
目标 commit（如果已知）：待你指定；若未知，可通过版本映射或显式传参处理
是否允许锁定本地 VS Code 版本：建议默认“是”
```

### 方案 B：不预置 server，只优化首次初始化体验

说明：

- 不尝试预埋 `VS Code Server`。
- 优化镜像内容，例如常用工具链、shell、git、语言依赖、扩展缓存、工作目录结构。

优点：

- 维护成本更低。
- 对客户端版本变化更稳健。

代价：

- 首次连接仍可能下载 server。

请补充：

```text
是否选择：建议默认“不选”
你希望预装哪些工具或扩展：如后续需要，可作为第二阶段补充
```

### 方案 C：同时支持在线与离线模式

说明：

- 在线环境默认按需下载。
- 离线环境通过构建参数、挂载缓存或制品仓库注入指定 server。

优点：

- 灵活。

代价：

- 实现复杂度和文档成本更高。

请补充：

```text
是否选择：建议默认“不选”
在线环境约束：默认公网可访问官方制品
离线环境约束：第一阶段暂不覆盖
制品存放位置：如未来需要，建议使用内部制品仓库或对象存储
```
